# Virtual EV benchmark results

!!! warning "What this is, and is not"
    These results show **internal consistency** (the energy account closes, the answer converges as the step shrinks, a run reproduces), **plausibility** (consumption and power are in a sane range) and **software performance** on one machine. They are **not** validation against a physical vehicle, a real CAN network or a security audit, and nothing here should be read as a prediction for a real car. Timings are indicative: one run, one machine, no repeats.

Generated by `scripts/benchmark_ev_drive.py`; reproduce with:

```bash
python scripts/benchmark_ev_drive.py --write docs/ev_benchmark.md
```

Measured with bms 0.65.0, Python 3.13.5, NumPy 1.26.4, SciPy 1.16.1, 8 logical CPUs, Windows-11-10.0.26200-SP0.

## Virtual CAN output

The `udds` cycle published over the in-process virtual bus and decoded with `cantools` and the shipped `bms.dbc`: 1,370 samples, 9,590 frames sent, 9,590 received, 0 missing, decode within tolerance: **True**. Send, receive and drain ran at 23,743 frames/s on this machine; that figure measures the software path, not any real bus.

The SOP power field is 16-bit watts in the shipped DBC, so it saturates at 65,535 W for this pack in 1,370 of 1,370 samples. The publisher counts this instead of hiding it.

## Telemetry gateway

Over loopback HTTP against a real uvicorn server. The publisher, the server and every client run in one Python process and share its GIL, so adding clients lowers each client's speed, and the multi-client row says little about the gateway's capacity with clients in separate processes. These measure the software path only.

| Clients | Records | Elapsed s | Per client records/s | Aggregate records/s | All received |
|---|---|---|---|---|---|
| 1 | 5,000 | 0.73 | 6,822 | 6,822 | True |
| 4 | 5,000 | 5.77 | 866 | 3,465 | True |

Latency from `publish` to the client receiving the record, at 100 records/s (500 of 500 received): median 1.33 ms, 95th percentile 1.77 ms, 99th 1.92 ms, worst 2.63 ms.

A client that connects late replays 5,000 buffered records in 878 ms (5,694 records/s), including connection setup.

Token issue runs at 51,691/s and verification at 45,348/s on one core. A token is 204 characters and one record is 177 bytes of JSON.

## What these results do not show

- That the vehicle model matches any real vehicle: its parameters are generic and illustrative.
- Anything about timing, load or arbitration on a real CAN network.
- Gateway behaviour across a real network, under many clients, or under attack.
- Performance on other hardware, or run-to-run spread: each figure is a single run.
